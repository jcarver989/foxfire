# Proposal: One Settings view for desktop, iOS, and web

## Overview

Move Foxfire desktop's existing Settings dialog into `foxfire-ui` and use it from all three apps. Today the iOS app and browser demo share a hosted shell with default theme preferences but no Settings entry point. Add the same **Settings** gear to their thread sidebar, next to Refresh.

All three apps get **Appearance** (**System**, **Light**, **Dark**) and a choice of built-in **Light theme** and **Dark theme**. Desktop keeps **Reduce motion** and **Interface size**; iOS and web don't show those rows in this release. A phone gets a scrollable sheet with a visible **Done** button; desktop and desktop-width web get a dialog with **Done** and Escape. Layout follows input and available space, not which app is running. A touch browser uses the same settings UI as iOS.

Changes apply and save as you make them. Choosing a dark theme while the app is light saves it without switching appearance. Closing Settings preserves the sidebar, selected thread, and any draft. Web reloads and iOS relaunches restore the choice before showing the main app. Settings are local to the browser profile/origin or installation; demo conversations still do not persist.

## Technical Approach

- **Share the entry button and the entire Settings view.** Move the desktop view and its existing rows into `foxfire-ui::ui::settings`. Render it from a typed `SettingsModel`: a required `SettingsField<ThemePreference>`, optional `SettingsField<bool>` for reduced motion, and optional `InterfaceSize` handle. A `SettingsField<T>` pairs a reactive read (`Memo<T>`) with a change callback (`Callback<(T,)>`). Hosts provide values and setters, not view fragments. If iOS later needs an option of its own, add a typed capability and a shared row; don't import UIKit, desktop `Registry`, or platform checks into the settings widgets.
- **Share theme selection; adapt presentation.** Keep `ThemePreference`, `ActiveReviewTheme`, the same built-in theme catalogue, and one picker handle/commit path using Clankerdiff's `theme_picker` and Rouge's `SearchPicker`. Pointer layouts retain the searchable popover and keyboard preview. Touch layouts place the same picker content in the Settings body, without the auto-focused search field or keyboard hints, and show a visible **Back** action. Clicking, tapping, or activating a choice commits it; leaving an uncommitted preview restores the saved theme. There is no separate iOS or web implementation of a setting.
- **Keep storage out of the view.** Desktop keeps its existing registry, state schema, and interface-size behavior. The hosted shell reads and writes a `ThemePreference` under `hosted-appearance` via Rouge `Storage`. The launchers use `app_storage("foxfire")`: origin-local storage on web and app-container Application Support on iOS. Missing or unreadable data uses defaults. An unknown or wrong-appearance theme ID falls back to the default for that slot without discarding the other slot. If storage isn't available, preferences still work for the current session.
- **Fix System mode at the Rouge platform boundary.** Browser Rouge already listens to `prefers-color-scheme`. On iOS the pinned Winit `Window::theme()` returns `None`, so Rouge needs to read UIKit's `traitCollection.userInterfaceStyle` at startup and in its existing native environment sync, which runs again when the app becomes active. Preserve the iOS 16 minimum and leave UIKit's own style alone. Foxfire's Settings view only sees Rouge's `appearance()` signal.

## Implementation Steps

1. **Extract Settings and migrate desktop first.** Move the desktop view into `foxfire-ui/src/ui/settings.rs`. Expose `settings(model, on_close)` and a shared `settings_button(on_open)` built on the existing gear button. In desktop, replace the local view with an adapter: bind `state.theme` and `state.reduced_motion` using registry memos/setters and pass `InterfaceSize::current()`. Keep the existing menu, shortcut, modal dispatch, and registry schema; bind the existing shortcut hint to the shared gear. Move theme preview/restoration into the shared view using `ActiveReviewTheme`; remove the now-unused desktop theme wrapper. Keep existing Settings test IDs and run the desktop settings tests before adding another host.
2. **Make the shared view usable on touch.** Keep one definition of the rows, theme selection model, picker, and commit/cancel callbacks. Add **Done** to the shared dialog/sheet. Use Rouge's presentation information to place the picker in the popover for pointer input and in the body for touch; use the same `SearchPicker` with search and key hints enabled only for pointer input. The touch list scrolls within the available height and **Back** dismisses the picker without committing. Keep keyboard preview, Escape order (picker, then Settings), and click-outside restoration on desktop and pointer web. Check small screens without relying on hover, Escape, or a soft keyboard.
3. **Wire the hosted model and Settings entry point.** Extend `hosted_view(backend, platform, storage)` and `demo_view(storage)` to take `Rc<dyn Storage>`. Install `ActiveReviewTheme` at the hosted window root with the system default. Read the stored preference once, normalize the palette IDs, and apply it before revealing the shell. Bind the loaded preference to the shared model with neither optional row. On a real change update the signal, then issue `Storage::write` immediately in change order (the file backend queues writes). Don't write on load, no-op selection, preview, or OS appearance changes. Reuse the shared gear and add the shared Settings view to the shell overlay so toggling it does not rebuild the thread or composer. Have both launchers pass `rouge::persist::app_storage("foxfire")`; component tests pass `MemoryStorage`.
4. **Connect UIKit appearance in Rouge before shipping iOS.** In the sibling Rouge checkout, override `Ios::appearance(window)` and `Ios::sync(window, ui)` in `platform/ios.rs`. Read from the UIKit view obtained through Winit's raw window handle on the main thread while the window is alive. Map Dark and Light to Rouge's `Appearance`, with Light as the fallback for unspecified/unavailable style. In sync call `ui.set_appearance`, which ignores unchanged values. Verify launch in Dark and changes made while the app was backgrounded. Leave other native hosts and the web listener alone. Document the shared entry point, local persistence, and updated `web_view` API in the README.

## Testing Plan

- **Desktop regression:** Run the existing Settings tests without changing their expectations for the shortcut, reduce motion, interface size, theme selection, preview/commit, cancel, and saved state. Confirm the current desktop preferences load without migration.
- **Shared interaction:** Exercise the same view through the hosted harness at wide pointer and phone touch sizes. Verify the common rows are present, desktop-only rows are absent, the picker scrolls on phone, and Done, Back, and pointer Escape dismiss the right layer. Verify an existing thread/draft survives changing appearance, closing Settings, and returning from the sidebar.
- **Theme and persistence:** Drive Rouge's window appearance through Light and Dark. Verify System follows it, fixed modes ignore it, and editing the inactive palette only changes the active palette when that appearance is used. Check colors or the active theme, not just the selected control. Seed `MemoryStorage` and check the first hosted frame; change mode and palette, rebuild, and verify both restore. Cover missing data, malformed JSON, and invalid theme IDs. Verify startup, previews, and OS appearance changes don't write settings.
- **Actual hosts:** Build with `scripts/build-web`; test reload, browser developer-tools color-scheme changes, and blocked storage. On an iPhone simulator or signed device, check a narrow portrait display and landscape, launch while iOS is Dark, change OS appearance while the app is backgrounded, then force-quit and relaunch after setting a fixed mode and non-default palette.

## Additional Notes

This adds appearance choices to web and iOS without removing any desktop options. Account sync, custom theme import, and exposing more settings to hosted users are separate decisions. The platform-specific work is limited to storage wiring and Rouge's UIKit appearance bridge; the settings controls, copy, and option behavior live together in Foxfire UI.
